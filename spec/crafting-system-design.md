# クラフトシステム設計書

## 1. 文書の目的

本書は、`docs/todo.md` に記載されたクラフトシステムを今後実装するための設計を定義する。現行モックアップの仕様を記録する `spec/current-specification.md` とは異なり、本書の内容は未実装である。

## 2. 目的と対象範囲

### 2.1 目的

- 所持素材をレシピに従って消費し、クラフトを実行できるようにする。
- クラフトによってインベントリ容量を段階的に拡張できるようにする。
- レシピを画面ロジックから分離し、JSONで追加・調整できるようにする。

### 2.2 初回実装の対象

- レシピ一覧の読み込みと検証
- レシピごとの必要素材、所持数、作成可否の表示
- インベントリ拡張レシピの実行
- 実行時の素材消費、容量変更、選択状態の整合、および結果通知

### 2.3 初回実装の対象外

- 通常アイテム、建築物、消耗品の作成
- 作成時間、作業台、スキル、レシピ解放条件
- 一括作成、作成予約、取り消し、素材の代替
- クラフト済み設備の砂浜またはマップ上への配置
- セーブ、ロード、およびサーバーとの状態同期

## 3. 基本方針

- インベントリの初期容量を現行の8枠から **16枠** に変更する。
- 既存のデバッグ用「＋4枠」操作と24枠の上限は廃止し、容量拡張はクラフトだけで行う。
- 容量は従来どおり、アイテムの種類数ではなく所持個数の合計で消費する。
- 初回のクラフト成果物はインベントリへ加えるアイテムではなく、インベントリ容量を更新する恒久効果として扱う。
- 容量拡張は **16 → 32 → 64 → 2000 → 9999** の順にのみ実行できる。途中段階の省略、同じ段階の再実行、容量の低下は認めない。
- ゲーム状態は現行仕様と同様にメモリ上だけで保持するため、ページ再読み込み時には容量も16枠へ戻る。

## 4. 用語と状態モデル

| 用語 | 意味 |
| --- | --- |
| レシピ | 必要素材と実行結果をまとめた定義 |
| 必要素材 | 実行時にインベントリから消費するアイテムと個数 |
| 現在容量 | `state.inventory.capacity` が保持する利用可能枠数 |
| 目標容量 | レシピ実行成功後に設定する容量 |
| 作成可能 | 前提容量を満たし、かつ必要素材をすべて所持している状態 |

レシピ定義は起動後に読み取り専用として扱う。所持数、現在容量、選択中アイテムIDは既存のゲーム状態を正とし、作成可否をそれらから都度算出する。作成可否を別の状態として保持しない。

## 5. レシピデータ

### 5.1 配置場所

レシピは `mockup/data/craft_recipies.json` に配置する。`recipies` は一般的な英単語の綴りとは異なるが、todoで指定済みのファイル名を互換性のため採用する。

### 5.2 JSON構造

```json
{
  "recipes": [
    {
      "id": "inventory-32",
      "name": "大きい木の箱（容量32）",
      "description": "インベントリ容量を32枠に拡張する",
      "ingredients": [
        { "itemId": "driftwood", "quantity": 8 }
      ],
      "effect": {
        "type": "inventory-capacity",
        "requiredCapacity": 16,
        "targetCapacity": 32
      }
    }
  ]
}
```

| フィールド | 型 | 制約・用途 |
| --- | --- | --- |
| `recipes` | 配列 | 1件以上のレシピを格納する |
| `id` | 文字列 | レシピ内で一意。状態判定やDOM識別に用いる |
| `name` | 文字列 | 一覧と実行結果に表示する名称 |
| `description` | 文字列 | レシピの効果説明 |
| `ingredients` | 配列 | 1件以上。素材ごとに `itemId` が重複してはならない |
| `ingredients[].itemId` | 文字列 | `items.json` に存在するアイテムID |
| `ingredients[].quantity` | 整数 | 1以上の必要個数 |
| `effect.type` | 文字列 | 初回実装では `inventory-capacity` のみ許可する |
| `effect.requiredCapacity` | 整数 | このレシピを実行できる現在容量 |
| `effect.targetCapacity` | 整数 | 成功時の容量。`requiredCapacity` より大きい値とする |

未知のフィールドは将来拡張のため無視してよいが、必須フィールドの欠落、型違い、ID重複、未定義素材、不正な個数または不正な容量を検出した場合はレシピデータ全体の読み込みを失敗とする。部分的に有効なレシピだけを表示してはならない。

### 5.3 初期レシピ

| ID | 表示名 | 前提容量 | 必要素材 | 目標容量 |
| --- | --- | ---: | --- | ---: |
| `inventory-32` | 大きい木の箱（容量32） | 16 | 流木 × 8 | 32 |
| `inventory-64` | 大きい木の箱（容量64） | 32 | 流木 × 16 | 64 |
| `inventory-2000` | サイロ（容量2000） | 64 | レンガ × 800 | 2000 |
| `inventory-9999` | ワームホール（容量9999） | 2000 | 惑星のコア × 1、宇宙ひも × 1 | 9999 |

レシピは表の順でJSONへ記載し、画面でも定義順を維持する。レンガ、惑星のコア、宇宙ひもは現行の `items.json` に存在しないため、クラフト実装前にアイテム定義と入手経路を別途追加する必要がある。

## 6. 作成可否の判定

各レシピは次の順で状態を判定する。

1. 現在容量が `targetCapacity` 以上なら「作成済み」とする。
2. 現在容量が `requiredCapacity` と一致しなければ「前段階が必要」とする。
3. 各必要素材について所持数が必要数未満なら「素材不足」とする。
4. 上記のいずれにも該当しなければ「作成可能」とする。

「作成可能」の場合だけ作成ボタンを有効にする。所持数はインベントリのスタックから `itemId` ごとに求める。複数素材のレシピは、すべての素材を満たした場合に限り作成可能とする。

## 7. クラフト実行処理

作成ボタン押下時は、表示時点の判定結果を信用せず、最新状態を使って次の処理を同期的に行う。

1. レシピが読み込み済みであることを確認する。
2. 現在容量と全素材の所持数を再検証する。
3. 条件を満たさない場合は状態を変更せず、理由を状態欄へ表示する。
4. 条件を満たす場合は、すべての必要素材をインベントリから差し引く。
5. 数量が0になったスタックをインベントリから削除する。
6. 消費によって選択中アイテムのスタックがなくなった場合は、選択を解除する。
7. `state.inventory.capacity` を `targetCapacity` に設定する。
8. インベントリとレシピ一覧を再描画し、作成物名、消費素材、および新容量を状態欄へ表示する。

素材消費と容量更新は一つの不可分な操作として扱う。検証後に処理を完了できない場合はどちらも変更しない。容量は加算ではなく目標値への代入とし、二重クリックなどによる重複拡張を防ぐ。

## 8. 画面・操作設計

- 既存のインベントリ領域に「クラフト」セクションを追加する。
- 各レシピに、名称、説明、必要素材の「所持数 / 必要数」、目標容量、状態、および「作成」ボタンを表示する。
- 素材不足の個数は視覚的に区別し、ボタンを無効にする。色だけに依存せず状態文も表示する。
- 前提容量に到達していないレシピは内容を確認できる状態で表示し、「前の容量拡張が必要」と案内する。
- 作成済みレシピは一覧に残して「作成済み」と表示し、ボタンを無効にする。
- ボタンの有効・無効は、漂着物の回収、砂浜への再配置、またはクラフトによって所持数・容量が変わるたびに更新する。
- キーボード操作と支援技術でも状態が分かるよう、作成操作にはネイティブの `button` と `disabled` を使用し、結果は既存の状態欄で通知する。
- レシピ読み込みに失敗した場合、クラフトセクションだけにエラーとHTTPサーバーからの起動案内を表示する。既存の漂着・インベントリ操作は、アイテム定義の読み込みに成功していれば継続可能とする。

## 9. 初期化とデータ読み込み

1. インベントリを容量16で初期化し、通常画面を描画する。
2. `items.json` を読み込み、既存仕様に従って検証する。
3. アイテム定義の読み込み成功後に `craft_recipies.json` を読み込む。
4. レシピを構造検証し、すべての `itemId` をアイテム定義と照合する。
5. 成功時はクラフト一覧を描画する。失敗時はクラフトだけを利用不可にする。

この順序により、レシピが未定義アイテムを参照していないことを起動時に検出できる。

## 11. 受け入れ条件

1. 新規起動時のインベントリ容量が16である。
2. 流木が7個以下では容量32の作成ボタンが無効で、8個なら有効になる。
3. 容量16かつ流木8個で容量32を作成すると、流木を8個消費して容量が32になる。
4. 容量32の作成後、そのレシピは作成済みとなり再実行できない。
5. 容量16では、容量64以降の素材を所持していても前段階不足で実行できない。
6. 容量32かつ流木16個で容量64を作成すると、流木を16個消費して容量が64になる。
7. 容量64かつレンガ800個でサイロを作成すると、レンガを800個消費して容量が2000になる。
8. 容量2000かつ惑星のコア1個と宇宙ひも1個でワームホールを作成すると、両方を消費して容量が9999になる。
9. 複数素材のうち一方でも不足している場合、素材も容量も変化しない。
10. 消費後に数量0となった素材は一覧から消え、その素材を選択中だった場合は選択が解除される。
11. ボタン連打または作成済みレシピの再操作で、素材の重複消費や容量の重複更新が発生しない。
12. レシピJSONが不正な場合は理由を表示してクラフトを利用不可にする一方、漂着物の回収など既存機能は利用できる。

## 12. 実装順序案

1. アイテム定義とレシピJSONを追加し、読み込み・検証処理を作る。
2. 初期容量を16へ変更し、既存の手動拡張操作を撤去する。
3. 作成可否判定と、素材消費・容量更新を行う純粋な処理を作る。
4. クラフト一覧と状態表示を追加し、既存のインベントリ更新処理へ接続する。
5. 受け入れ条件に沿って境界値、前提順序、複数素材、二重実行、読み込み失敗を確認する。
6. 動作確認後にREADMEと現行仕様書を更新する。
